# #1039 步驟 0：延後測試能改寫成「對答案目標」的比例（2026-11-22）

結論：在這份樣本上，照設計 v3 現有的觀察方式，31 個測試 commit 只有 1 個（3%）能整個改寫成對答案目標，未達開始步驟 2 的條件。依設計「太少就先停、回報」，步驟 2 先不開工。最大的阻礙是 78% 的測試要靠執行 CLI 子程序、替換函式或程序與訊號才能觀察結果，而目前的 `probe` 只能直接呼叫函式。

設計：#1039 設計 v3（issuecomment-7073287663）。本報告只做計數，不含程式。

## 樣本
- 來源：Cairnwork 在一個內部工具 repo 上的 31 次實跑（每次一個測試 commit）。31 個 commit 全部取回，0 個取不到。
- 單位：新增或改動的測試函式共 196 個（Python 檔以 AST 列出；兩支 shell 腳本測試各算 1 個）。
- 方法：靜態閱讀判斷，沒有在 base 上執行。「base 上有牙齒」是估計。

## 分類規則（設計 v3）
- **A**：能寫成 probe，至少一個強鍵，而且估計 base 上該強鍵的值不同或不存在。
- **B**：能寫成 probe，但只有弱鍵（bool、None、[-16, 16] 的整數、最多一個字元的字串、空容器、`observe_raises`）。
- **C**：有強鍵，但強鍵在 base 上相同（沒有牙齒）。
- **D**：不靠 pytest 的機制就寫不出來（細分原因見下）。
- **E**：取不到或判斷不了。

## 結果

| 類別 | 測試函式 | 比例 |
|---|---|---|
| A 強鍵、估計有牙齒 | 21 | 11% |
| B 只有弱鍵（拒收） | 21 | 11% |
| C 強鍵沒有牙齒（拒收） | 1 | 0.5% |
| D 寫不出來 | 153 | 78% |
| E 取不到或不清楚 | 0 | 0% |

D 的原因：
- 以子程序執行 CLI，結果在結束碼、標準輸出或寫出的檔案：100；
- 替換函式（monkeypatch、mock）：41；
- 程序存活：5；
- 訊號：5；
- 牆鐘時間：2。

commit 層級（31 個）：
- 所有新增或改動的測試都在 A（可整個改寫）：**1（3%）**；
- 至少有一個 A：10；
- 至少有一個 D：27（87%）；
- 只有 B：2；只有 D：17。

## 讀法與限制
- **B 拒收的 21 個中，12 個其實有自然的強觀察值**（比對到的文字、回傳的 dict 或 list），只是原測試只斷言了 bool 或長度。人改寫時多半能補上強鍵，所以 B 的拒收率高估了實際損失。
- **A 的 21 個中，15 個呼叫的是這次才新增的函式**，「base 上不存在」就算有牙齒；真正比較既有行為差異的只有 6 個，其中 1 個信心低，可能屬 C。
- **樣本偏差**：來源只有一個以 CLI、排程與檔案為主的工具 repo，D 會偏高；函式庫型的 repo 比例可能較好。大 commit 主導函式層級的計數（最大的幾個分別加了 23、17、14 個測試）。
- 若設計允許 probe 執行子程序並把標準輸出或寫出的檔案內容當字串觀察（設計 v3 的未決問題之一，`observe_file`），100 個子程序類 D 中會有一部分轉成 A 或 B；本輪沒有重算。
- 以手動設定模組變數取代 `monkeypatch.setattr` 的測試算 A；用 `monkeypatch` 或 `mock.patch` 的算 D。

## 下一步（交 layer1 決定）
1. 依設計的停止條件，步驟 2 不在現有觀察方式上開工。
2. 兩個可行方向（擇一或都做），都只需計數、不寫程式：
   - (a) 在函式庫型的 repo 上再抽一份樣本，確認比例是不是只有這個 repo 偏低；
   - (b) 先定案「子程序標準輸出與檔案內容可當觀察值」，再用同一份樣本重算。
3. 步驟 1（`tamper_scan` 文件寫明殘餘類別並各補測試）與本結果無關，可照原排程做。
