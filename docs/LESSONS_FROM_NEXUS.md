# 從 Nexus-new 學到的教訓

Cairnwork 是 Nexus-new 的後繼產品。下面每一條都是 Nexus-new 真的犯過的錯，後面接著 Cairnwork 的規則。開工前先讀完。

## 1. 假完成

**Nexus-new 的狀況**：2026-10-17 對 11 個 repo、2,018 張 PR 的稽核發現，「宣稱完成，其實沒完成」的 PR 確認下限是 6.6%，推估 8%～10%。治理規則訂得多嚴，跟假完成的比例沒有關係，真正抓得到的是實際使用和獨立審查。

**規則**
- 只有 nexus-core 的 VERIFIED 才算完成，而且這個 VERIFIED 必須綁定 Core 實際驗證過的那一個 commit（`notary.verdict(..., expected_candidate=)`）。
- 「測試全綠」「審查通過」「我已經修好」都不算完成。
- 宣稱接好了、修好了之前，先在真實入口跑一次，貼出證據。

## 2. 以為接上了，其實沒接上

**Nexus-new 的狀況**：
- 8/6 的一次改動讓規劃器只拿到 2 個特徵，任務一律落到 L1，過了兩個多月才發現。
- 10/19 盤點第一層能力時，只有 xray 真的有在跑。

**規則**
- 每一條保障都要做突變測試：把那道檢查拿掉，至少要有一個測試因此失敗。拿掉之後沒有任何測試失敗，就代表這道檢查沒有被保護。
- 改完檔案後確認修改真的寫進去了（grep 或 `git diff`），不要只相信工具回報「成功」。2026-10-19 Cairnwork PR #3 就發生過：一段修改因為格式化工具先改了程式碼而沒套用上，是審查用實際測試才抓到的。

## 3. 紀錄被覆蓋

**Nexus-new 的狀況**：公證紀錄用 `INSERT OR REPLACE` 寫入，後來的 VERIFIED 可以蓋掉先前的 FAILED（Nexus-new#2776，截至 2026-10-19 尚未修復）。

**規則**
- 判決、收據、證據一律只能新增，不能修改：用 UNIQUE 限制加上禁止 UPDATE／DELETE 的 trigger，也禁止對已經存在的鍵再做 INSERT。
- 同一次嘗試的第一個結果就是最終結果。換了證據，就開一次新的嘗試。

## 4. 把錯誤吞掉

**Nexus-new 的狀況**：程式裡有 169 處 `except Exception: pass`，例如帳號池的狀態檔讀不到時，會被當成「沒有帳號」。

**規則**
- Ruff BLE001／S110 開著。真的需要接住例外時，在那一行寫明理由，並把它記錄成「失敗」。
- 允許降級運作的情況，要寫在契約裡，不能臨時在 except 區塊裡自己決定。

## 5. 巨型檔與重複實作

**Nexus-new 的狀況**：
- 有一個 3,152 行的函式，還有一個 2.2 萬行、每天都有人改的 bench 腳本。
- `capability_registry` 有兩份，而且已經分歧；I/O 小工具的私有副本大約有 70 份。

**規則**
- CI 強制限制：單檔 ≤400 行、單函式 ≤80 行、核心 5,000 行為警戒預算（超過發 WARNING，PR 須說明原因、替代方案、責任、成本、驗證；不得為避開計數器新建 `cairnwork_*` 套件）、不准循環 import。
- 一件事只有一個正本。要搬進來時，舊的那份在退出線上後凍結，不要留兩份一起長。

## 6. 數字好看，但量錯了

**Nexus-new 的狀況**：歷次「Nexus 帶來提升」的數字，在 2026-10-19 的稽核中全部被判 DROP。原因包括：只有 Nexus 組有手寫答案、隱藏測試的結果回饋給了 agent、題目被調過、評分出錯、資料遺失。10/14 那場 A/B 雖然公平，但 Nexus 的能力全部關著，等於沒有量到 Nexus。

**規則**
- 能力要在 Cairnwork 自己的 A/B 裡贏過裸骨幹才能升格。兩組條件必須對稱：同樣的題、同樣的模型、同樣的評分器，門檻事先登記。
- 受測的一方不得接觸隱藏測試和評分器。
- README、發布說明、PR 描述只寫已經量到的結果。

## 7. 照抄舊程式

**Nexus-new 的狀況**：17 個檔案裡寫死了主機路徑（其中可能有一部分是刻意的部署契約），port 則散落在 41 個檔案裡。

**規則**
- 從對方的協定或規格重新實作，不要整段複製。例如 Cairnwork 的 Core 公證是照 nexus-certify 公開的 generic verification 協定寫的，不是複製 Nexus-new 的 transport。
- repo 是公開的，所以主機路徑、內部 IP、帳號 email、token 都不能進 repo。

## 8. 治理比產品長得快

**Nexus-new 的狀況**：合併規則、anchor、簽章、lane 區塊一層一層疊上去，其中簽章和 lane 區塊後來都退役了。

**規則**
- 一條新的關卡，要先說清楚它擋住的是哪一種真實會發生的錯誤，並附上評估證據：用真實資料量誤擋率，用另外寫的案例量偵測率。
- 能用一條 CI 規則或一個測試擋住的，就不要另外造一套機制。

## 9. 審查要對抗式，而且要動手試

Cairnwork 前三張 PR，每一輪獨立審查都抓到真的 bug：
- 已取消的任務可以被改回進行中；
- 已驗證的嘗試可以換一個改動重送，照樣拿到通過；
- 呼叫端可以自己捏造改動集合；
- 已通過的紀錄被複製到別的任務，也會被讀成通過；
- 新資料庫被同時打開時，初始化有競態問題。

**規則**
- 審查的人要實際寫 probe 去重現問題，不是只讀程式碼。
- 高風險 PR 要多一個不同模型做對抗審查，最多三輪；過了三輪，刻意構造出來的繞法用反駁處理，不再改程式。
- 審查者的說法也要驗證。Gemini 曾宣稱「isolation_level=None 時 in_transaction 恆為 False」，在 Python 3.11 和 3.12 實測都不成立。

## 10. 每條規則各自正確，合在一起卻無法同時成立

**Nexus-new 的狀況**：Nexus-new#2999：一次線上任務的五個階段全部完成、驗證也通過，整體卻仍被擋下。原因是規劃器把任務標成一種類型，執行環境的契約卻要求另一種類型。兩邊各自都有道理、各自的測試都綠，但沒有任何測試從入口一路跑到最終判定，所以合起來的矛盾到線上才被發現。

**規則**
- 新增或修改契約時，要附一個從入口一路跑到最終判定的測試，或一份演練紀錄（`docs/drills/`）。
- 只測單一環節的測試，不能拿來證明環節之間彼此相容。
